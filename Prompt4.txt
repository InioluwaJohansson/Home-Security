### Caller

When a user starts a call:

1. Obtain the user's microphone and camera using:

```javascript
navigator.mediaDevices.getUserMedia({
    audio: true,
    video: true
});
```

Respect the existing call type. For an audio call, request only audio.

2. Create an `RTCPeerConnection`.

3. Add all local media tracks:

```javascript
stream.getTracks().forEach(track => {
    peerConnection.addTrack(track, stream);
});
```

4. Configure STUN:

```javascript
{
    iceServers: [

}

Keep the configuration easy to extend later with TURN.

```

through the existing SignalR `IceCandidate` method.

6. Create the SDP offer:

Send:

CallId

Sdp

through the existing SignalR `Offer` method.

### Receiving an Offer

Listen for the existing SignalR `Offer` event.

Before processing the event:

```javascript
if (dto.personId === currentPersonId) {
    return;
}
```

Never process an offer generated by the current user.

For an offer from another participant:

1. Get/create the appropriate `RTCPeerConnection`.
2. Set the remote description.
3. Obtain the local media stream.
4. Add the local tracks.
5. Create an answer.
6. Set the local description.
7. Send the answer through the existing SignalR `Answer` method.

### Receiving an Answer

Listen for:

```text
Answer
```

Ignore the answer if:

```javascript
dto.personId === currentPersonId
```

Otherwise:

```javascript
await peerConnection.setRemoteDescription({
    type: "answer",
    sdp: dto.sdp
});
```

### Receiving ICE Candidates

Listen for:

```text
IceCandidate
```

Ignore candidates originating from the current user:

```javascript
if (dto.personId === currentPersonId) {
    return;
}
```

Otherwise add the candidate to the correct peer connection:

```javascript
await peerConnection.addIceCandidate(
    new RTCIceCandidate({
        candidate: dto.candidate,
        sdpMid: dto.sdpMid,
        sdpMLineIndex: dto.sdpMLineIndex
    })
);
```

Handle candidates that arrive before the remote SDP has been set by temporarily queueing them and adding them after `setRemoteDescription()` completes.

### Group Calls

The application supports group calls.

Do not assume there is only one remote peer.

For group calls, maintain separate `RTCPeerConnection` instances for each remote participant, keyed by `PersonId`.

For example:

```text
peerConnections[personId]
```

Incoming offers, answers and ICE candidates must be associated with the correct remote participant.

Since the current backend DTO only contains `PersonId` and does not contain `ToPersonId`, initially use the existing `PersonId` to identify the sender and ignore messages originating from the current user.

Do not break the existing SignalR implementation.

### Call Lifecycle

Respect the existing API-based call lifecycle:

* `StartCall` → starts a ringing call.
* `JoinCall` → accepts/joins the call and transitions it to Connected.
* `RejectCall` → only used while the call is Ringing.
* `EndCall` → used when a connected participant leaves.
* A timeout is handled by the backend and results in a Missed call.

WebRTC connection setup should happen at the appropriate point in this lifecycle and must not incorrectly mark calls as connected or ended.
